## Arquitectura propuesta

`render.yaml` define un único servicio web Render Python, una instancia y un disco persistente de 1 GB. `runtime.cloud` inicia Streamlit y supervisa opcionalmente `runtime.cloud_runner`. El dashboard abre la base en modo lectura y nunca ejecuta scheduler ni crea órdenes. El runner, desactivado por `AI_FLOOR_CLOUD_RUNNER=0` y `AI_FLOOR_SCHEDULER=0`, toma un lock exclusivo junto a la SQLite antes de ejecutar. El supervisor termina si muere un proceso hijo y, cuando el runner esté habilitado en una etapa posterior, comprueba su heartbeat. El endpoint `/_stcore/health` comprueba el proceso web; el heartbeat y `runtime.cloud --preflight` comprueban el runner y los gates operativos.

El disco se monta en `/opt/render/project/src/data/runtime`; `AI_FLOOR_DB_PATH` apunta dentro del disco. La base, journal, outbox y lock viven juntos. Una sola instancia evita autoridad duplicada y el límite de disco no compartido entre servicios. El plan `starter` y el disco son una propuesta de configuración, sin compra ni despliegue. Render no ofrece almacenamiento persistente en su filesystem efímero; el plan free no admite discos. Ver [Render disks](https://render.com/docs/disks) y [free tier](https://render.com/docs/free).

## Slack y recuperación

`notification_events` se persiste antes del envío. `notification_deliveries` reclama cada `event_id` antes de llamar al webhook; un reinicio no reenvía el mismo evento. La entrega es **at-most-once**: una caída entre el claim y el envío puede dejar un intento sin entrega; el evento persistido sigue consultable y auditable. Los fallos de Slack no alteran la decisión de trading. Se envían trade opened/closed, rechazos de riesgo, fallos/recuperación, reinicio, awareness macro HIGH y resumen diario; no se generan alertas rutinarias `NO_SETUP`. Solo se envían summaries permitidos, IDs y metadatos, sin razonamiento privado. Ver [Slack incoming webhooks](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks).

## Preflight, despliegue y rollback

El preflight separa `INFRA_READY` de `experiment_ready`. Infraestructura exige PAPER, ejecución real deshabilitada, símbolos y configuración de proveedores, una sola instancia, scheduler/runner apagados, macro `none`, contraseña del dashboard, disco realmente montado, ruta SQLite bajo el mount, `quick_check`, escritura transaccional y experimento no iniciado. Las credenciales de OpenAI/Twelve Data/Slack se comprueban aparte. `macro_provider_certified=false` es un gate explícito en este hito; por ello `experiment_ready=false` incluso con infraestructura lista. El proceso web se niega a arrancar si falta infraestructura y tanto supervisor como runner se niegan a activar el experimento. El preflight local ordinario devuelve `NOT_READY` por falta de mount Render; una prueba offline con mount simulado comprueba `INFRA_READY` sin habilitar el scheduler. En Render deberá repetirse la comprobación con el disco real. Antes de cualquier activación futura se necesita certificar un proveedor macro y preparar una copia SQLite consistente mediante SQLite backup API en almacenamiento privado. La persistencia del disco no sustituye backups. Para rollback, mantener scheduler y runner en `0`, restaurar código compatible con schema 3 o un backup consistente en el mismo disco. No bajar schema sobre una DB viva.
